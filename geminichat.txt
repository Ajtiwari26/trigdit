Step 1: Automated Theme Scraper & Asset Downloader
When a user inputs their live URL or imports their extracted folder, your Python/Node.js backend hits the target pages to read the clean DOM tree.

You need to extract the raw HTML, crawl every connected asset (CSS stylesheets, Google Fonts, and images), and download them locally to rewrite their paths.

// backend/services/scraper.js (Node.js + Cheerio example)
import axios from 'axios';
import * as cheerio from 'cheerio';

export async function scrapeTargetSite(url) {
  const { data: html } = await axios.get(url);
  const $ = cheerio.load(html);

  const assets = { images: [], styles: [] };

  // Find and download all images to store them in your public folder
  $('img').each((i, el) => {
    const src = $(el).attr('src');
    if (src) assets.images.push(src);
  });

  // Find all internal and inline stylesheets
  $('link[rel="stylesheet"]').each((i, el) => {
    const href = $(el).attr('href');
    if (href) assets.styles.push(href);
  });

  return { html, assets };
}
Step 2: AST Node Splitter (Converting HTML into Visual Blocks)
You cannot allow the user to drag and drop single letters; it will break the layout. You must segment the HTML page into top-level sections using an Abstract Syntax Tree (AST) parser.

Your parser scans the HTML body for block containers like <section>, <header>, <footer>, or <div> elements with specific layout classes (like Tailwind or Bootstrap containers).

JavaScript
// backend/services/parser.js
import { parse } from 'html-parse-stringify';

export function splitHtmlToSections(rawHtml) {
  // Parse HTML string into a queryable JSON object tree
  const ast = parse(rawHtml);
  
  // Filter top-level structural elements inside the <body> tag
  const dynamicSections = ast.map((node) => {
    if (node.type === 'tag' && (node.name === 'section' || node.name === 'header')) {
      return {
        id: `section_${Math.random().toString(36).substr(2, 9)}`,
        type: node.name,
        rawHtml: stringifyNode(node), // Helper to turn JSON node back to HTML string
        contentData: extractEditableText(node) // Extract innerText to map to input boxes
      };
    }
  });
  return dynamicSections;
}

// template-repo/app/components/DynamicSection.jsx
import React from 'react';

export default function DynamicSection({ rawHtml, contentData }) {
  let processedHtml = rawHtml;

  // Dynamically inject updated text fields straight into the compiled code block
  Object.keys(contentData).forEach((key) => {
    processedHtml = processedHtml.replace(key, contentData[key]);
  });

  return (
    <div 
      dangerouslySetInnerHTML={{ __html: processedHtml }} 
      className="visual-section-wrapper"
    />
  );
}

The Two Approaches to Changing the Actual Code
Just like code-review-graph uses Tree-sitter to parse code files into a structural map (Abstract Syntax Tree or AST) without reading every word, your tool will scan a frontend project to map out the visual components.

When a user changes a text input in your editor, you have two ways to handle how that code compiles:

Approach A: The "Pure Code Modifier" (Exact Code Rewriting)
This matches your description exactly. When the user edits text, your platform parses the actual source code of that specific component file and directly rewrites the text strings inside it.

How it maps: Your tool indexes Hero.jsx. It notes that line 14 contains the <h1> tag.

When the user edits: The editor sends a command: "In Hero.jsx, change the text inside <h1> to 'Summer Sale'". Your backend modifies the actual React file, pushes the change to GitHub, and Vercel compiles the fresh raw component code perfectly.

The Catch: This is an incredibly smart approach, but code can be highly unpredictable. If a developer conditionally writes code like <h1>{isPromo ? "Sale" : "Welcome"}</h1>, a simple text-rewriting engine can get confused and break the component's internal logic, causing a Vercel build compilation failure.

Approach B: The "Data-Driven Component Map" (The Robust Industry Standard)
Instead of altering the React/HTML code strings directly, your scanner enforces a rule where the component reads its text from an isolated data file, and your editor only rewrites that data file.

How it maps: Your scanner parses the repository and automatically registers the structure: "Hey, I found a component called Hero.jsx and it uses a variable called hero_title".

When the user edits: Your editor writes directly to a centralized content.json file inside the repository.

How it compiles: The actual code of Hero.jsx never changes; it just reads dynamically from {content.hero_title}. Because the structural syntax of the code files remains 100% untouched, Vercel will compile it perfectly every single time with zero risk of broken tags or syntax crashes.
